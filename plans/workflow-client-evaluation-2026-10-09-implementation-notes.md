Architecture assessment: use the product interaction contract as the criterion for both implementations. Workflow state/progression belongs to the server; client-specific event normalization and local permissions belong to adapters/hooks. A genuine host restriction may deny an otherwise valid action, but must remain a distinct capability/policy block with pending state preserved. Both codebases can require changes: repair hook admission/reminders, and expose authoritative source state in consumable projections where absent. Do not make server capture/report semantics imitate a stale hook policy merely to get a green client run.

Tradeoff: aligning hooks to an authoritative contract preserves cross-client state/audit consistency but requires projection/version compatibility and native tests. Adapting source to a hook can be appropriate when the hook reveals a genuine product or host constraint; doing so solely to retain current denials would sacrifice the declared capture/report/retry semantics. Independent implementations without a shared contract retain drift risk.
