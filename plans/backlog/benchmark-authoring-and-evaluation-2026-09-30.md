## Decisions and intent

Desired state: an optional capability that guides authors from a real problem to a validated frozen benchmark and a reviewable comparison, reusing those systems.

1. Build **contracts and a scaffold-and-validate authoring workflow first**. A prompt assists authors; executable validators and independently checked evidence determine readiness.
2. Preserve `resource_manager` as the resource authority and `prompt_engine` as the workflow authority. Do not add another prompt catalog, chain language, scheduler, or delegation policy.

5. Improve representativeness, protected holdouts and human calibration before expanding orchestration. Existing all-pass cases increasingly become regression checks.
6. Continue local coding comparisons first. Connected MCP/plugin workflows, interactive interviews, visual quality, model routing and premium-coordinator economics are separate experiments.
7. Behavior changes are proposed in draft PRs with an explicit evaluation disposition before active resources, rules, skills or hooks change. Local planning and isolated candidate construction are preparation, not deployment. Passing checks does not itself authorize merge or promotion.

This plan authorizes no deployment, public publication, model spend, policy promotion, or migration of the live runtime database. The proposed branch name reserves no git ref. Save the plan locally now; bind a concrete implementation slice when this backlog item is activated.

## Change proposal and evaluation loop

`Observed incident or explicit hypothesis → evidence bundle → task contract and evaluation plan → isolated candidate + draft PR → validated checks and controlled comparison → review disposition → merge/deploy → production feedback`

Every proposed change has an evaluation disposition: reuse an adequate existing case, add a missing case, or explain why a non-behavioral change needs only mechanical validation. A new benchmark and paid batch are not required for every typo or documentation edit. A behavior-changing proposal without an observable success criterion is not ready for promotion.

| Boundary             | Reviewable output                                                                                                          | Authority / exit condition                                                                                                                                        |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Propose              | Problem or optimization hypothesis, affected behavior, evidence and counterevidence, expected benefit, falsifier, rollback | Author proposes; existing issue is linked when available. Do not create an issue solely to satisfy paperwork when the PR already owns the proposal.               |
| Establish evaluation | Reused/new task IDs, public requirements, grader/control revisions, quality/cost/latency criteria, budget and known limits | Cases derive from requirements and observed failures before candidate outcomes; independent challenge of new graders.                                             |
| Build candidate      | Branch/worktree and early draft PR; base/candidate revisions and scoped diff                                               | No direct live configuration changes. Draft may expose open questions; it does not imply implementation or benchmark readiness.                                   |
| Validate             | Offline checks first, then budgeted agent trials when model behavior is in scope; immutable report/artifact references     | Pin the exact revision evaluated. Candidate, fixture, environment or evaluator changes invalidate the corresponding prior evidence; rerun only affected coverage. |
| Review               | Accepted, rejected, deferred or inconclusive decision with limitations, exact evaluated revision and rollback              | Human review controls promotion; a gate verdict, search score, passing CI or model-written approval cannot self-authorize merge.                                  |
| Observe              | Deployed revision, production corrections/rework and rollback observations                                                 | Feed verified failures into new regression proposals; retain null/negative results and rejected candidates.                                                       |

Proposed PR evidence summary: **why this change; linked evidence/counterevidence; evaluated base/head and resource hashes; existing/new cases; results and uncertainty; rollout/rollback**. Reference immutable reports rather than copying changing numeric tables into several locations. A PR head change requires evidence to be checked against the new head; unrelated checks may be reused with an explicit impact analysis. A merge result that differs in evaluated resources needs corresponding revalidation before activation.

Validation scales with the claim. Parser or schema fixes need deterministic positive/negative controls; routing, wording, skill-loading and delegation claims need representative agent cases; connected workflows need pinned integration state. Existing spending and publication authority remains applicable within its scope. PR creation, benchmark execution, merge and live deployment are distinct acts; record what is already authorized rather than asking again at every stage.

## Conversation and issue evidence contract

The first useful tool capability is **turning selected history into a source-linked incident bundle that can be reviewed and reproduced**. Parsing and indexing support that outcome; merely making all conversations searchable does not create a trustworthy evaluation.

Normalize source client/schema/parser version, host-qualified conversation/session/turn identity, parent-child linkage where actually established, event/message role, timestamp, original locator plus event/line/byte span and content digest. Preserve requests, assistant claims, actual tool results, user corrections and later resolutions as distinct event kinds. Store import watermark and original source revision so incremental imports are idempotent and edited/truncated sources do not silently change old evidence.

Each curated bundle includes the reported symptom, observed behavior, desired behavior and its authority, unresolved hypotheses, counterevidence, relevant constraints, proposed reproduction and an evidence-confidence disposition. A reviewer confirms the contract before a case is generated. Incomplete traces and assistant assertions remain explicitly unverified; duplicate quotes, inherited child history and multiple messages from one incident do not become independent sightings.

Issue/PR links are repository-qualified IDs with URL, fetched time, source revision/content digest and exact supporting spans. Distinguish **mentions**, **supports**, **reproduces**, **contradicts**, **resolved by** and **supersedes**. Extracted `#123` text or semantic similarity creates a candidate link, not a verified causal association. Preserve issue revisions and later corrections. Existing agent-workbench conversation-to-plan associations remain authoritative; import their identifiers rather than maintaining a competing registry.

Imported transcripts and issue text are evidence, not current instructions or authorization. Do not execute embedded commands, adopt quoted policies, or treat an old user approval as permission for a new operation. Separate raw capture integrity from authenticity: hashes detect changed bytes, but trusted host bindings/source access establish provenance.

Case derivation creates public requirements and a bounded starting state, with private reference solutions/oracles and a reviewed requirement-to-criterion map. Exclude the source conversation's solution patches, later successful outputs and holdout answers from the candidate-visible fixture. Preserve the incident-to-case mapping privately when source material cannot be published. Exposed incidents are development/regression evidence; protected holdouts use separately selected sources unavailable to candidate tuning or retrieval.

Evaluate this evidence tool separately from downstream agent performance: source/role/lineage parsing accuracy, exact citation resolution, idempotent imports, issue-link precision, contradiction/missing-evidence handling, redaction and solution-leakage controls, and retrieval relevance on a small human-reviewed query set. Semantic similarity may rank candidate evidence; it does not certify truth, expected behavior or rule redundancy. Return bounded excerpts with source IDs and locators; do not inject entire histories into every task. Track ingestion, curation and evaluation overhead separately, and avoid default background model runs on every conversation or commit.

## Repeatable benchmark authoring

`Real need/failure → public task contract → fixture/reference solution → independent graders and controls → adversarial contract review → validated frozen version → controlled trials → comparison → promotion decision`

1. Select actual repository failures and changes, reduced to bounded reproductions while retaining the integration boundary that caused the failure. Record source provenance and why the task represents real usage. Weight by observed workload where available; otherwise label weighting as a design assumption.
2. Assign development, regression, capability or protected promotion-holdout status. Track exposure and tuning history. Once results guide changes, that case is development evidence; do not relabel it untouched. Keep holdout artifacts inaccessible to candidate agents and treatment authors as appropriate.
3. Map each criterion to a public requirement, observable outcome, evaluator, severity and limitation. Keep private test values private, not required behavior. Ensure reference solutions pass and valid alternative implementations are accepted.
4. Challenge graders with distinct plausible failures, including shortcuts that look correct without using the intended integration. Reject irrelevant imports/setup failures as proof that an agent wrote effective regression tests. Existing C8–C11 controls provide examples to reuse.
5. Have an independent reviewer challenge solvability, hidden assumptions, leakage and false positives before freeze. Preserve that review alongside positive, negative and valid-alternative controls.
6. Freeze task, environment, tools, evaluator and resource revisions before outcomes. Generate task registration and readable docs from the typed contract to prevent manual count/schema drift.
7. Validate offline in isolation, then execute the approved experiment. Publish capability results separately from regression results. A saturated case can remain a useful regression test without being made artificially harder.

Add balanced behavioral pairs in a later dataset slice: should ask versus proceed on sufficient evidence; should stop versus authorized continuation; useful delegation versus unnecessary coordination; current versus stale handoff recovery. Use a scripted user oracle for interview tests so branches and response costs are reproducible. C7 alone cannot support an interview claim.

Robustness variants should preserve requirements while varying wording, irrelevant context or benign repository layout. Keep them linked to the original family; they do not count as wholly independent tasks. Start with local deterministic cases; add connected-service versions only after service/resource revisions and the existing MCP runtime issue are pinned and resolved.

## Metrics and experimental design

**Primary economic metric:** total priced cost of all measured attempts, including failed attempts, retries and descendant agents, divided by accepted logical tasks. With no accepted tasks, report the metric as undefined with total spend and zero successes. Report actual invoice cost only when supported; label API-equivalent estimates and pricing assumptions separately.

Price output, uncached input, cache reads and provider-specific cache writes at the applicable rates, currency, date and service tier. Include reasoning tokens according to provider billing semantics. Preserve token counts alongside prices so results can be repriced. Report authoring, grading and reviewer spend separately; do not quietly claim inference-only cost is total project cost.

| Dimension    | Report                                                                                                                                      | Decision use                                                                                               |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Quality      | First-attempt acceptance; criterion failures; critical boundary violations; unknown/infrastructure outcomes; consistency across repetitions | Quality guardrails precede savings; no weighted score that allows cheap failure to offset broken contracts |
| Cost         | All-attempt cost, cost per accepted logical task, billing-type distribution, parent/child split                                             | Compare within each client and model policy; keep pricing uncertainty visible                              |
| Time         | Task execution, setup, grading/review and end-to-end duration separately; timeouts/cancellations                                            | Prevent shorter request metrics from concealing extra turns or recovery work                               |
| Behavior     | Turns, tool errors, repeated work, clarification/stop/delegation decisions with native evidence                                             | Explain outcomes; skill usage and rule compliance alone earn no quality credit                             |
| Code quality | Integration behavior, compatibility, type contracts, meaningful regression tests and calibrated review                                      | Do not use LOC, test count or style preference as stand-ins for maintainability                            |
| Production   | User corrections, rework and code survival with contextual review                                                                           | Check external validity; code survival is not a sole correctness metric                                    |

Use matched tasks/variants and common controls across arms, balanced order and an explicit cache policy. Record cache state as observed when a reset cannot be guaranteed. Preserve failures and missing cells in denominators; do not compare only successful intersections without also reporting exclusions.

Predeclare quality non-inferiority margins, critical-failure rules, minimum evidence, uncertainty method and stopping rules before a promotion experiment. Margins and acceptable budget remain owner decisions. Paired differences and task-family clustering are preferable to treating every repetition as independent; four task families cannot support a broad statistical guarantee. Report uncertainty and inconclusive outcomes honestly. A zero observed regression is not proof of zero regression.

Avoid tuning and evaluating on the same cases. Package comparisons establish marginal package value; later controlled ablations are needed to identify which rule, hook or consolidation actually helps. Semantic similarity can suggest consolidation candidates, but cannot establish behavioral redundancy. Each proposed removal needs an observed failure/benefit hypothesis, a falsifier, a flagged treatment and rollback.

Calibrate graders with an owner-reviewed sample covering good, bad and borderline outputs. Hide treatment labels for review and record reviewer identity/type, rubric and disagreements. Agent review remains labeled agent review until human calibration exists. A model judge version change invalidates direct grade comparability unless regraded/calibrated.

## Open decisions and deferred scope

- **Packaging:** optional module/package location, dependency installation and archive root; settle via E1, preserving the server's existing install boundary.
- **Resource surface:** use ordinary canonical prompts plus validated evaluation artifacts initially. Introduce a new resource type only if lifecycle/consumer needs justify the public API change.
- **Promotion policy:** acceptable quality margin, critical violations, required breadth, human calibration sample and uncertainty method; decide before a promotion run, not after seeing savings.
- **Immediate experiment:** exact treatment refs, checkpoint and provider readiness; these remain unset in the draft template.
- **Representativeness:** choose real incidents and workload weights from an inventory; do not invent a production distribution from synthetic test results.
- **Portability:** current host namespaces and pinned toolchains are useful isolation, not proof of fully hermetic cross-machine reproducibility. Container/Harbor export can follow a stable contract.
- **Later evaluations:** connected MCP workflow/service revisions; balanced stop/interview scenarios; visual outcomes; premium coordinator/worker mix; a standardized follow-up edit as an agent-plus-code maintainability probe. None is measured by the upcoming compact batch.
