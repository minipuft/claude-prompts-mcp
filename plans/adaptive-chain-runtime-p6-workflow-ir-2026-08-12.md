**Master plan**: `adaptive-chain-runtime-2026-08-09.md` §P6 · finalizes **D1** · consumes ledger findings **P3-F5**, **P4-F2**, **P5-F2**, **P5-F3**, **P5-F5**, **P7-F6**

## Charter as found (verbatim, master plan §P6)

> **Goal**: a client model can submit a graph (nodes, edges, gate bindings, budget caps) that the server validates against schema + budgets and executes as a chain run.
> **Opens with**: the D1 decision, finalized against real schemas.
> **Research questions**: IR schema as a contract artifact (`tooling/contracts/`), validation depth (DAG-only, bounded fan-out, max nodes — the bounded-IR posture from the design review); relationship between submitted IR and durable chain resources; whether budget ceilings are enforceable or advisory (D6 says advisory, but token ceilings per step may be checkable server-side against declared costs).
> **Acceptance**: malformed IR rejected with actionable errors; valid IR executes through the P3/P4 machinery with no IR-specific execution path (IR compiles TO the runtime, it doesn't bypass it).

## Intent

- **Work type**: feature (Workflow IR) · **secondary**: bug_fix (five deferred findings, three of them live defects)
- **Problem**: the only structured way to submit an ad-hoc multi-step run is a string grammar that cannot express the fields P3/P4/P5 added (`id`, `visibility`, `inlineGateIds`, `inputMapping`/`outputMapping`, `retries`, `agentType`); and the fields that DO exist in YAML are unreachable on the direct invocation path (P5-F5), positionally mis-resolved after mutation (P6-F1), or leak past withholding (P5-F2).
- **Risk**: high — Tier 5 adds a Public API union member and a third command source to a 22-stage pipeline that must behave identically under two instance lifetimes; Tiers 1-3 change observable behavior for shipped chains.
- **External deps**: none.
- **Confidence**: high on Tiers 1-3 (probed defects, small blast radius), medium on Tiers 4-6 (the IR shape is an owner decision, OQ-P6-1/2).

### Acceptance clauses

- **(a)** A client submits a workflow IR through the declared tool surface and the server executes it as an ordinary chain run — no IR-specific execution path. Observed as: `chain_runs` + `chain_run_nodes` rows structurally identical to a YAML chain's, terminal `execution_records` telemetry populated by the same writers.
- **(b)** A malformed IR is rejected with typed, actionable rejections naming the offending node/edge and the rule violated, and **nothing is written** — no run row, no session, no version.
- **(c)** Structural budget caps are **enforced** at validation with named reasons; declared cost/token ceilings are **recorded only**, never enforced (D4 record-don't-model, D6 advisory).
- **(d)** An IR node can carry every step field the runtime actually consumes — node id, gate binding, visibility, delegation (`subagentModel`/`agentType`), input/output mapping — and each is observable in the resulting run. This is the clause that makes P5's visibility policy client-reachable for the first time (measured: **zero** shipped resources declare `visibility:`).
- **(e)** YAML `subagentModel` marks a step delegated on a plain `>>chain` invocation (P5-F5), demonstrated live rather than by direct pipeline construction.
- **(f)** (a)-(e) proven by **(i)** one acceptance suite against **real collaborators** (real `SqliteEngine`, real registrar, real `ResponseAssembler` — the P5 5.1 / P7 6.1 precedent) **and (ii)** a live drive over **BOTH STDIO and Streamable HTTP** as a blocking verify step. Designed in from Tier 1, not appended: **P7-F14 was invisible to mocked-seam suites and only a real engine saw it; P5-F5/F6 were found only by a live client drive.**

## Constraints (bind every tier)

- **Transport parity** (project CLAUDE.md §3): STDIO pins one `McpServer` per connection, HTTP builds a fresh one per request. All IR run state lives in SQLite; nothing may hang off a registered instance, and no IR cache may live on the tool object.
- **Pipeline state** via `context.gates` / `context.frameworkAuthority` / `context.diagnostics`; never mutate arrays directly. Stages stay thin orchestration; IR validation/linearization/compilation are **owner-service** work, not stage work (Domain Ownership Matrix).
- **Contracts as SSOT**: hand-written Zod is the validation SSOT; `tooling/contracts/*.json` is the description/metadata SSOT; never edit `_generated/`; regenerate via `npm run generate:contracts`.
- **Public API Contract**: `prompt_engine` parameter additions are union ADDITIONS (non-breaking); removals are breaking. The tool surface is the union of every reachable shape.
- **MCP tooling only** for prompt/chain resources — no direct edits under `server/resources/prompts/**`.
- **Validation minimum per tier**: `npm run typecheck && npm run lint:ratchet && npm run typecheck:tests:ratchet` + a scoped `npm run test:match`. Full `test:ci` / `validate:all` / `validate:arch` / both SQLite gates / `build` / `verify:mcp` / `test:e2e` at Tier 6.
- **Docs lockstep**: named per tier below.
- **Probe hazard (P7-F4)**: `rg` honors `.gitignore`; every probe under `server/resources/` needs `--no-ignore` or it silently omits 103 of 131 prompts. Carry this in every worker brief.
- Never commit without approval.

### Root causes (probed, file:line)

**P5-F5 — delegation is unreachable on the direct path.** `06-operator-validation-stage.ts` has **three** early exits, not one: `:33-36` (blueprint restored), `:39-42` (no parsedCommand), and `:46-49` (`operatorSet` empty). `normalizeDelegation` runs at `:53`, after all three. `parsedCommand.operators.operators` is populated only on the **symbolic** parse path (`04-parsing-stage.ts:85-102`); the **direct** path (`:105 buildDirectCommand`) writes `subagentModel` onto steps at `:164-166` and leaves `operators` empty. So a plain `>>chain` hits `:46-49` and returns before `markDelegatedStepPrompts` (`:136-143`) ever sets `step.delegated`. Both delegation renderers gate on `delegated === true` (`chain-operator-executor.ts:495`, `response-assembler.ts:512`), and nothing reads `subagentModel` without that check first. `markDelegatedStepPrompts` reads **only** `parsedCommand.steps` and never touches `operatorSet` — so hoisting it alone is safe; `syncDelegationToOperators` (`:146-155`) genuinely needs `operatorSet` and must stay below.

**Survey the owner ruling required** (`rg --no-ignore -l "subagentModel|agentType" server/resources/`): **exactly one file** carries either field — `server/resources/prompts/development/code_review_test/prompt.yaml:45`, `subagentModel: fast` on chain step 2 of 4 (`promptId: research_docs`). **Zero** resources declare `agentType`. **Zero** declare `visibility:`. 17 shipped resources define `chainSteps`. So the hoist changes observable behavior for **one step of one chain out of seventeen**.

**P4-F2 — the blueprint's node identity is an accident, not a contract.** `ParsedCommandSnapshot.steps` (`chain-session.ts:53-70`) declares exactly three optional fields: `inlineGateIds`, `args`, `visibility`. No `nodeId`. **But** the runtime value stored in that slot is a `ChainStepPrompt`, which _does_ carry `nodeId` (minted `04-parsing-stage.ts:147,155`), and `buildChainNodes` reads it through a cast (`13-session-stage.ts:352-368`). The identity survives the `JSON.parse(JSON.stringify(...))` clone at `13-session-stage.ts:411-413` by accident of serialization, not by declaration. The real cost is downstream: `response-assembler.ts:403-417 resolveHandoffVisibility` indexes `steps` **by array position** (`nextStepIndex`), precisely because the type offers no id — so it mis-resolves after any P4 insertion or skip (→ **P6-F1**).

**P5-F2 — named outputs are unnamespaced and unmarked.** `text-refs/index.ts:71-81` writes `namedOutputs[chainId][name] = content` for every key of a step's `outputMapping`; `buildChainVariables` (`:112-135`) `Object.assign`s them flat into the same bag as `step1_result`, `chain_id` and ordinary args at `:130`. `stripChainHistory` (`chain-operator-executor.ts:798-807`) can therefore only delete regex-identifiable positional keys, and the code says so at `:792-796`. A withheld `chain_history` leaks through any named alias.

### Premise corrections (untrusted-inventory — every claim below contradicts an inherited one)

1. **There is no graph runtime.** Probed: zero hits for `dag|acyclic|topolog|adjacency|cycle detect` across `server/src/`. `chain_run_nodes.position` is a total order; no step type anywhere carries `condition`, `next`, or `goto`. The charter's "submit a graph … executes as a chain run" can only mean **edges compile to an order**, or the acceptance clause "no IR-specific execution path" is violated. This is the headline decision (OQ-P6-2).
2. **P4-F2 is smaller than the ledger says, and its real cost is somewhere else.** "The persisted blueprint cannot be addressed by node identity" — the identity is _present_ (JSON round-trip) and _read_ (via cast). What is missing is the declaration, and the live damage is positional handoff-visibility resolution (P6-F1).
3. **P5-F3 is one finding, not three** (table above). Two clauses are falsified at HEAD.
4. **The alternative destination for P5-F1/P5-F3 no longer exists.** The ledger routes both to "reader-without-producer sweep (F14) or P6". That sweep is complete and classified `reference`: `plans/reference/techincal_debt/reader-without-producer-sweep-2026-08-05.md:256` — "F9 ✓, F11 ✓, F13 ✓, F14 ✓ — this sweep is complete."
5. **P5-F1 is dual-owned and is NOT P6's by default.** It was re-found as S-F1 in `subagent-delegation-contract-2026-08-12.md`, whose **Tier S1 states "the decision is the tier"** (wire the producer or delete the field). P6 records the coupling and does not touch it (OQ-P6-6).
6. **The deferral list handed to this plan is incomplete.** The ledger also routes **P3-F5** ("P4 design …, **P6 IR budgeting**") and **P7-F6** ("engine-layer follow-up (post-P7 or **P6 IR validation**)") here. Both are chartered below.
7. **IR is not a new submission surface; it is the structured superset of an existing one.** The symbolic command language already submits ad-hoc multi-step runs with per-step gates, framework, style and delegation — and has its own first-party contract artifact (`tooling/contracts/registries/operators.json`). What it cannot express is exactly the P3/P4/P5 field set. Stating this keeps the phase honest about what it buys.
8. **`outputMapping` does not do what the docs say** (→ **P6-F2**). `docs/reference/chain-schema.md:24` says it "renames this step's output for downstream use". `text-refs/index.ts:71-81` assigns the **whole step content to every key** and never reads the mapping's values. 9. **D1's "resource type like prompt/gate/methodology" understates the cost.** Measured: adding a `resource_type` touches 7-8 files and creates a **fourth** copy of one enum (`resource-manager.schema.ts:30`, `resource-manager/core/types.ts:57`, `resource-manager.json` parameters[0], `version-history-service.ts:13`) with no generated linkage — the exact drift class that produced P7-D1.
10. **`tooling/contracts/` has no first-party resource-shape artifact.** Every first-party contract is a tool parameter list; the only schema-shaped files are vendored third-party (`vendor/agent-plugins/1.0.0/*.schema.json`) and `registries/operators.json` is a registry, not a schema. An IR contract would be the first of its kind, with no loader or consumption idiom to slot into (OQ-P6-10).

## Design

**Objective**: give a client a validated, structured, node-addressed way to submit a multi-step run, and close the five deferred findings that stand between the current runtime and that submission being expressible at all.

**Non-goals**: branching/conditional execution (no runtime, premise correction 1); a fourth MCP tool (D1 default); a new SQLite table (budgets ride existing counters + telemetry); wiring `inlineGateIds` (OQ-P6-8); the engine-layer `required` gap beyond IR (P7-F6 stays open); P5-F1 (owned by the delegation plan); P5 residual row 4.5.

**Pre-flight** (probed, not recalled). **3 failures → compound: `contracts` + `defined` + `reuse-scope` → the step shape has four hand-maintained copies and three sequential strippers; an IR that adds a field to one of them is dead. Re-scope first: the IR compiles to ONE declared target, and any new step field is added at all three strippers in the same row.**

## Findings (for the master plan's Findings Ledger)

- **P6-F1** — `resolveHandoffVisibility` (`response-assembler.ts:403-417`) resolves the delegated step's visibility declarations by **array position** (`nextStepIndex`) into `ParsedCommandSnapshot.steps`. After any P4 insertion or skip, position and node no longer correspond, so it reads another step's declarations. A live defect: adaptive mutation ships. Closed by Tier 2.4.
- **P6-F2** — `outputMapping` values are never read. `text-refs/index.ts:71-81` assigns the **whole step content** to every key of the mapping, so a two-key mapping publishes the same content twice under different names. `docs/reference/chain-schema.md:24` describes a rename that does not happen. Ruled by OQ-P6-5.
- **P6-F3** — `ChainOperator.hasDelegation` is write-only: written at `06-operator-validation-stage.ts:169` and `symbolic-operator-parser.ts:485,495`, **zero readers** in `src/`. A fourth instance of the write-no-reader shape, structurally invisible to `validate:state-field-writers`, which catches the opposite polarity.
- **P6-F4** — **P5-F3 is one finding, not three.** `step.metadata['gateInstructions']` has a reader (`chain-operator-executor.ts:476-480`, `d39fdb74`, Dec 2025 — predating P5) and `hasBlockingGates` has a reader (`13-session-stage.ts:215`). Only `perGateVerdicts` is genuinely unread. A ledger row that overstates a finding gets a phase budgeted against work that does not exist.
- **P6-F5** — `06-operator-validation-stage.ts:18` declares `Can Early Exit: No` while the stage has three early exits. The stale marker sits directly above the exit that made P5-F5 invisible for two phases.
- **P6-F6** — a `prompt_engine` parameter withdrawn by runtime narrowing is **silently stripped by Zod, not rejected** (`prompt-engine.schema.ts:387-392`). Any future runtime-gated parameter inherits silent-drop: the client gets a success with its parameter discarded. Avoided here by never narrowing `workflow`; the general shape stays open.
- **P6-F7** — three sequential strippers stand between chain-step authoring and runtime: Zod `.strict()` (`prompt-schema.ts:209`), the `normalizeChainSteps` allowlist (`yaml-prompt-loader.ts:383-405`), and the stage-04 projection (`04-parsing-stage.ts:148-181`). A field added at fewer than three is silently dead — the chain-step form of P7-F2.
- **P6-F8** — the chain step shape is maintained in **four** hand-written copies (`ChainStepSchema` `prompt-schema.ts:128-209`; `ChainStep` `shared/types/index.ts:637-666`; the loader mirror `yaml-prompt-loader.ts:55-75`; `ChainStepPrompt` `operators/types.ts:12-59`), with no generated linkage. ### changelog_entry

**Added** — `prompt_engine` accepts a `workflow` parameter: a structured, node-addressed workflow IR validated server-side against schema and structural budget caps, then compiled to an ordinary chain run. Invalid submissions are rejected with typed, addressed errors and write nothing. IR nodes can carry the step fields the symbolic command grammar cannot express — stable node ids, per-step visibility, gate bindings, delegation hints and input/output mappings.

**Fixed** — a step-level `subagentModel` declared in `prompt.yaml` now marks its step delegated on any chain invocation, not only after a `==>` operator. Handoff visibility is resolved by node identity instead of array position, so it stays correct after adaptive insertion or skip. Withholding `chain_history` now also removes outputs republished under an `outputMapping` alias.
