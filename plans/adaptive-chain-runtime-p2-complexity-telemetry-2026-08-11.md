# P2 — Complexity Telemetry (Record-Only): Implementation Plan

Master plan: `plans/adaptive-chain-runtime-2026-08-09.md` (Phase P2). Produced by `>>implementation_plan` chain `chain-implementation_plan#1`, 2026-08-11.
Location: in-repo `plans/` per this repo's established convention (P0/P1 precedent — the chain template's default target is `~/.claude/plans/`; kept in-repo for greppability and survival across compaction).

**Master decision D4 (binding on this whole plan)**: complexity is recorded, never modeled, until a named consumer of a score exists. No coefficients, no scoring formula, no routing decisions derived from any field this plan introduces.

## Phase 1 — Discovery (summary)

- **Writer inventory**: `executionRecordStore.append()` has exactly 3 call sites, not 2 as `execution-history-action-handler.ts`'s own docstring claims — `18-execution-stage.ts:173` (per-step `working` render), `21-formatting-stage.ts:50` inside `emitChainTerminalRecord()` (terminal `completed`/`cancelled`, gated by `resolveTerminalStatus()`), and `prompt-execution-pipeline.ts:102` inside `emitFailureRecord()` (terminal `failed`, the pipeline's single catch-all error boundary for all 22 stages).
- **Live value-dead precedent found**: `ExecutionRecord.gateVerdicts: GateVerdictSummary[]` (chain-execution.ts:134) is a REQUIRED field whose value is `[]` on every row today — none of the 3 writer call sites pass `gateVerdicts`, so `buildAppendParams` always defaults it. This is the exact trap `.claude/rules/sqlite-persistence.md` documents for `workspace_id`, previously unnamed for this column. Captured as a growth-capture item (see Phase 4-6).
- **Durable-counter gap**: the only existing durable counter for gate activity is `pendingGateReview.attemptCount` (manager.ts:1377, incremented inside `recordGateReviewOutcome()`), which is **deleted whenever `pendingGateReview` clears on PASS** — it cannot answer "how many total across the run." `chain_sessions`/`chain_run_registry` (where `ChainSession` ultimately persists) are both PID-scoped `ephemeral`/`derived` tables per `table-contracts.ts`, deleted at server-exit cleanup — so none of steps-planned, gates-fired, retries, or unknowns-opened/closed survive past the owning process unless captured onto `execution_records` (retention-capped but durable-for-history) at the moment they are true.
- **P1's ledger already sufficient**: `session.unknownsLedger` (landed P1) is already the cumulative source of truth for unknowns — entries are never deleted, only transitioned `active`→`resolved`. `unknownsOpened = ledger.length`, `unknownsClosed = ledger.filter(e => e.state === 'resolved').length`. Zero new `ChainSession` fields needed for this pair.
- **DI pattern precedent**: `deps.chainSessionStore` (the `ChainSessionService` singleton) is already injected into ~12 other stages at `pipeline-builder.ts`; `ResponseFormattingStage`'s own constructor call (`pipeline-builder.ts:334-339`) currently does NOT receive it — confirmed absent, not assumed.
- **Sibling pattern**: the `ExecutionRecordStore` writer pattern itself (3 call sites, append-only, best-effort/non-throwing per its own docstring) and the `recordGateReviewOutcome()` mutate→await`saveSessions()`→throw pattern in manager.ts. The P1 `gate_verdict` structured-object precedent does **not** apply — P2 needs no new `prompt_engine` parameter; every field is server-observable, not model-submitted.

1. `ChainSession` counter mutation rides the **existing** `recordGateReviewOutcome()` mutate → await `saveSessions()` → throw contract — unchanged, matches `architecture.md`'s state-mutation contract.

## Rulings (main thread, 2026-08-11 — supersede the open questions below)

1. **Q1 RULED — verdict-submission count.** `gatesFired` increments on every verdict submission; `gateRetries` on FAIL only. Scalar counters, no `Set`, matching the `attemptCount` pattern. Docs must name the semantic exactly: "gate verdict submissions."
2. **Q2 RULED — handler stays on `queryRecent()`; the view is NOT extended.** Measured 2026-08-11: `v_execution_history` has ZERO code readers — `rg` across `src/` and `hooks/` finds only its definition and contract entry; the declared reader (`execution-history-action-handler.ts`) reads `store.queryRecent()` at :54. Adding `steps_executed` or the 5 columns to a reader-less view repeats the value-dead defect class this table has produced twice already. Consequences: **Tier 1 row 4 shrinks** (DDL columns + SCHEMA_VERSION bump only — no view edit); **Tier 5 row 12 is unblocked** (compute executed in-handler as `COUNT(DISTINCT stepNumber)` over the session's already-returned records); **Tier 1 row 5 gains** a `finding` on the `v_execution_history` entry in `VIEW_CONTRACTS` stating the declared reader actually reads the raw table via `queryRecent()` and the view awaits a real consumer before gaining columns.
3. **Q3 RULED — out of scope.** `gate_verdicts_json` value-dead fix is a standalone debt-sweep candidate; do not fold into any P2 tier.

## Open questions requiring a main-thread ruling (RESOLVED above — kept for the record)

1. **Semantics of `gates_fired` vs `gate_retries`.** This plan defaults to: `gatesFired` increments on EVERY gate-verdict submission (PASS or FAIL); `gateRetries` increments ONLY when the outcome is FAIL (i.e., a retry cycle is about to happen). An alternative reading: `gatesFired` = count of DISTINCT gate IDs evaluated this run (not verdict submissions), which would require tracking a `Set<gateId>` rather than a scalar counter, and behaves differently when multiple gates are bundled into one `pendingGateReview` (the `gateIds: string[]` array on `PendingGateReview`). The chosen default is cheaper (one scalar increment, matches the existing `attemptCount` pattern exactly) but conflates "how many verdicts were submitted" with "how many distinct gates fired." **Ruling needed**: is verdict-submission-count the right semantic, or should `gatesFired` count distinct gate IDs via `pendingReview.gateIds.length` accumulated into a Set?
2. **Tier 5 wiring target.** Phase 1 confirmed the CURRENT `execution_history list` operation reads via `ExecutionRecordStore.queryRecent()` directly, NOT through `v_execution_history` — the view exists and is contract-declared as the reader for this handler, but Phase 2.5 did not re-verify whether the handler literally queries the view or the raw table. If it queries the raw table, adding `steps_executed` to the view (Tier 1 row 4) does nothing for this reader — the handler would need its own `COUNT` over already-returned records instead (as row 12 already allows as a fallback), OR the handler should be migrated to query the view for this operation. **Ruling needed**: migrate `listRecent()` to query `v_execution_history` (bigger diff, but makes the view the actual reader its own contract entry claims it is), or keep `queryRecent()` and compute `steps_executed` in the handler (smaller diff, but the view's `steps_executed` column becomes a second implementation of the same count with only ONE consumer using it, and that consumer isn't even it)?
3. **Value-dead `gate_verdicts_json` cleanup — in scope or deferred?** Phase 1 surfaced that `ExecutionRecord.gateVerdicts` has been value-dead since it shipped (no writer ever binds it). This plan does not fix it — fixing it is unrelated to the 5 new telemetry fields and would grow this plan's diff into another domain (per-record gate-verdict attribution, not run-level summary counts). **Ruling needed**: confirm this stays OUT of P2 scope and gets logged as a standalone debt-sweep candidate (growth-capture already flags it), rather than silently expanding Tier 3's diff to also fix it.
