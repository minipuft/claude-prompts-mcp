# Resource locations, hand edits and gate examples

## Now (2026-11-13)

Goal: a user keeps resources in labelled profiles that `cpm` manages and a client selects with one variable, the profile's config lists any further locations in one validated key, the server reports what it resolved and where it wrote, a file edited by hand gets the same guarantees as a tool write, and a command-checked gate ships the examples that prove it.
Slice: T3 on `feat/resource-locations-t3`: rows 3.1–3.5 done, boundary green (90 steps, unit 8131, integration 1919, verify:mcp 20/20), at its PR; row 3.6 opened from its findings. Merged: T1a #539, T1b #540, T4 #541. T2 rows 2.1–2.4 are built on `feat/resource-locations-t2` with its boundary green; its PR follows T3's merge.
Next decision: none open.
Constraint: Tier T1 changes what an existing variable serves, so it ships in 6.0.0. Tiers T2, T3 and T4 are additive and may land in 6.0.0 or the next minor. No new default directory is created under a user's home, and the server never writes a config file.

## Intent

**Work type**: feature with a breaking configuration change · **Risk**: medium — resource resolution decides what every prompt call can find.

Current state: five mechanisms across three channels decide where resources live (`MCP_WORKSPACE`, `MCP_RESOURCES_PATH`, `MCP_RUNTIME_ROOT`, the `prompts.directory` config key, a project's `.claude-prompts/` folder). Only `prompts.directory` is in the config schema, and it covers one of four resource types. Ten source files read `MCP_RESOURCES_PATH` from the environment directly. Setting it withholds the project folder at two sites in `server/src/runtime/paths.ts`. Neither `config get` nor status reports a resolved path or its source. A file changed on disk is detected, attributed as `filesystem` and reloaded, with no versioning call found in the hot-reload observer. `CLAUDE.md` forbids hand edits under `server/prompts/**`, a directory that does not exist. A skills export with `--client all` writes into, and registers, clients the operator left unregistered, and its preview omits the registration change. No gate definition carries an example of a passing or failing reply; 2 of 25 shipped gates run a command.

Desired state: a profile is a workspace folder: `config.jsonc`, `resources/<type>/` and runtime state. A client selects one profile by setting `MCP_WORKSPACE` to its path, and `cpm workspace` names profiles with labels in a registry file beside them; the server never resolves a label and reads the registry only to show the current profile and its siblings in status. The profile's config carries one `paths.resources` list in the schema: the profile's own folder is entry one, listed folders follow, the earlier entry wins a duplicate id, `"bundled"` is an explicit entry and a list without it serves only the listed locations plus the small set the server needs to run. A created resource lands in the project folder when one exists on STDIO, otherwise in the first location, unless a config key names another, and the tool result says where in one line. `MCP_RESOURCES_PATH` keeps one meaning for good, overriding the list with that one folder, and no shipped manifest sets it. A project folder always joins the stack on top and a project's own config may not set the list. A disk edit records a version and a failed load is visible in the change log and status. Export touches registered clients only. A gate may ship examples beside its definition, and the server runs them for command-checked gates.

Non-goals: retiring `MCP_RESOURCES_PATH`, a startup migration of any variable into a config file, a stacking verb or flag on `cpm workspace`, moving runtime state, executing examples for gates judged by the client model, changing how a workspace id is derived (owned by `plans/state-db-workspace-scope-2026-10-28.md`).

### Interfaces

```jsonc
// <profile>/config.jsonc, validated by config.schema.json
"paths": {
  // the profile's own resources/ folder is always entry one; earlier wins a duplicate id;
  // "bundled" is explicit; writes land in entry one unless writeTarget names a listed folder
  "resources": ["../shared/resources", "bundled"]
}
```

```jsonc
// <parent>/workspaces.jsonc, read and written by cpm; the server reads it for status only
{ "dev": "./dev", "shared": "./shared" }
```

```text
$ cpm workspace use dev
Set in your client config:  MCP_WORKSPACE=/home/you/claude-prompts/dev
```

```text
# every resource_manager create or update ends with one line
saved: /home/you/claude-prompts/dev/resources/prompts/review/prompt.md
```

```yaml
# resources/gates/<id>/gate.yaml
examples:
  - file: examples/pass.md
    expect: pass
  - file: examples/fail-missing-section.md
    expect: fail
```
