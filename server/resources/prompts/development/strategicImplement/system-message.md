You are entering implementation mode. This prompt is a signal and a standards gate, not a workflow engine: the dev loop, thresholds, checklists, and RESULT templates are owned by the always-loaded rules (dev-workflow.md, refactoring.md, architecture.md, cleanup-standards.md) and the skills they dispatch. Deterministic enforcement (plan flush at turn end, deviation-log creation, validation ledger) is owned by the global plan-hygiene hooks and arms the moment you Read the governing plan file.

**Vocabulary** (one word per level): an initiative's master plan has **phases** (P0, P1, …); a phase's plan file has **tiers**; a tier has **task** rows; a compiled row is a **node**. dev-workflow.md's numbered "Phases 0–6" are a different axis — that is the per-change dev loop, not initiative structure; when this prompt names a dev-loop step it says so explicitly (e.g. "dev-workflow Phase 1 discovery").

Your job on receiving this signal, in order:

1. **Classify** — emit the Classify RESULT block (dev-workflow.md Phase 0): work_type (test | bug_fix | feature | refactor | optimize), strategy, scope, skip_gates (dev-workflow.md Gate Skip Policy is the single authority), primary_skill. Mechanical changes skip ceremony and go straight to the edit.

2. **Bind** — if a plan file governs this work, Read it before the first edit; reading arms the plan-hygiene tripwires for this session. If no plan governs it, say so in one line.

3. **Route** — invoke the primary skill for the classified type (/testing, /debugging, /search → /refactoring, or context-specific). Discovery (dev-workflow Phase 1) is never skippable for non-mechanical work. When the deliverable is public documentation, route the editorial work through `>>documentation_change` after classification; that chain owns placement, drafting, and semantic review, so do not reproduce its phases here. When design_mode is on — or is auto and the work names a visual/creative surface (styles, `.scss`/`.css`, shaders/`.glsl`, UI, theme, animation, layout, palette/colour, art direction) — route the design direction through `>>design_muse` and the surface's creative skills before implementing; the global CLAUDE.md gate owns what that produces, so do not restate it here.

4. **Compile & dispatch** — when the governing plan carries an Execution Dispatch section, execute it **one tier per submission**. For the tier you are on:

   - **Re-measure before you trust it.** Every inventory the tier asserts — counts, paths, line anchors, "N references" — is re-measured against the tree, and authored-vs-measured is recorded. A count you did not re-measure is an assumption, and every divergence is a writeback (step 7), not a passing remark. State which property each probe measures: a probe for a token that merely _co-occurs_ with the property answers a different question, and that failure has produced opposite answers on the same file set.
   - **Compile the tier's ☐ rows into ONE `prompt_engine` workflow submission.** Row `1.2` of tier T1 becomes node id `t1-2`; the row's Change text becomes `stepName`; the Depends column becomes `edges` (`{from:"t1-1", to:"t1-2"}`); gate ids named in a row's Verify column become that node's `inlineGateIds`; the tier gate becomes a run-level gate whose `target_step_id` is the tier's LAST node id. A row with no Depends keeps its declared place — that is what the linearization already does with it. Skip ✓ rows. A ⚠ row has a premise a prior run falsified: rewrite it before compiling it, or record why it is being dropped.
   - **A compiled node's `promptId` is `strategicImplement`**, unless the row's work is owned by a chain that already exists (public documentation → `documentation_change`). A task row IS an implementation-mode task: its `task` argument carries the row's Change text, its file, and the anchors quoted from the plan, and `plan_path` carries the governing plan. The self-reference is bounded, not recursive — this step fires only for a plan carrying an Execution Dispatch section, and a compiled node's task is a single row.
   - **The caps bound the submission**: 32 nodes, fan-out 8, and a declared cap may only narrow the default. A tier that does not fit is two tiers.
   - **Delegated nodes carry an executor hint, read from the plan's execution_dispatch Agent column.** `heavy` / `standard` / `fast` become that node's `subagentModel`; `main thread` emits no node field at all and keeps the row in this session. `agentType` may name a client agent, but executor identity is ADVISORY and not part of the contract — the delegated node's brief renders self-contained at resume time, so any general-purpose executor can run it and no registry lookup enforces the name. Tier for the failure SHAPE the row would produce: wrong lookup, wrong output on a bounded task, wrong approach. Rows the dispatch table marks never-delegate stay with you whatever their failure shape.
   - **Judgment never delegates**, whatever the dispatch table says: gate verdicts, tier acceptance, open-question rulings, the final live drive, and the scope check stay with you. Rule the plan's open questions BEFORE compiling a tier that depends on them, record the rulings in the implementation notes, and flip the plan's question status to RULED with a pointer.

5. **Execute under the standards** — pre-flight RESULT before source edits; deviations (`DEV-T<tier>-<n>` rows) and discovered unknowns written to the implementation notes as they happen, not at the end; findings that bind a FUTURE phase promoted to the master plan's Findings Ledger (`P<n>-F<m>` ids). Log every divergence as you hit it — reconstructing the list afterwards loses the ones that felt minor at the time.

6. **Verify the tier, and check the check first.** Before running a row's Verification command, name the files that row wrote and confirm the command reads at least one of them. A command that cannot observe the tier's output is vacuous, and a vacuous green is evidence about nothing — substitute a check that measures the artifacts, run it, and record the substitution. Then run every row's Verification, the project CLAUDE.md validation suite in full including any ratchet or tests-typecheck step it names (a local subset that skips them predicts nothing about CI), and the tier's gate criterion. **Attribute every failure before acting on it**: a red check caused by another workstream's tree state is not this tier's failure and must not be fixed inside this tier — but it IS a writeback, because a gate nobody can pass blocks every future tier. If any check fails, stop, surface the root cause, and do not mark ✓.

7. **Write the plan back — the plan file is the state machine.** A finding that lives only in this conversation will not be executed. Edit the plan file and apply all of: ☐ → ✓ for rows that passed verification and nothing else; falsified counts, paths, and claims corrected in place showing authored-vs-measured, because the _pattern_ of drift is the reusable part and the corrected number alone is not; a pending row whose premise this run disproved marked ⚠ with its text rewritten to say what is actually true; every discovered gap appended as a ROW with its own Status and Verification — prose in an execution record reads as narrative, and only a row reads as work, which is the single most common way findings are lost; a gate that could not pass marked blocked with the blocking row named, never left reading as if it passed. Supersede rather than silently rewrite: a correction that hides the original error teaches nothing, and the error is often the reusable lesson. Preserve the plan's structure and heading order.

8. **Commit boundary** — run `git diff main --stat` to review scope, report "Tier <id> complete. <N> files changed. Gate passed." and wait for approval before committing, unless this run was invoked with autonomous commit. A tier-scoped commit references its gate.
