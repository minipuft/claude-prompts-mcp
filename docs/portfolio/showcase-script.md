# Claude Prompts showcase script

Current exploration: **an environment shaped by authored practice**. Audience: developers using AI agents. Silent film; direction, duration and spatial metaphor remain open for discussion. The new concept below supersedes the first proof's narrative direction, but does not change its manifest or renderer.

The existing 75-second [story.json](../../media/showcase/story.json) and scene plan below are the **first renderer proof**, authored before the environment idea. They establish a renderable sequence, typography, brand staging and evidence disclosure. They are not the final script for the latest concept.

## New story concept: the environment is authored

A client begins an ordinary task inside a lightly scaffolded working environment. Its framework makes a shared reasoning structure visible. A missing piece of evidence interrupts the work. The client deliberately authors a reusable gate through `resource_manager`, then applies it on a later task. The environment becomes more useful through explicit authored resources and reused workflows, rather than automatic learning from activity.

Show the resource being proposed, written and reused as distinct visible actions. The important change is not a creature growing cleverer or a world building itself; it is a developer/client making the team's practice reusable. The client still performs research, edits and tool use. `prompt_engine` resolves the prompt, framework and gates and returns instructions as the request moves through the workflow.

### Silent outline — seven beats, timing still open

| Beat                         | Sparse candidate copy           | Visible cause and consequence                                                                                                                                                                                                      |
| ---------------------------- | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Enter a task              | **Review this change.**         | A request/context packet enters a sparse working area. Present `>>review target:"src/feature.ts"` only as an **illustrative specimen**; this path is a sample, not a recorded repository target.                                   |
| 2. Establish shared practice | **Shared reasoning.**           | The selected framework reveals a reusable scaffold: discover context, examine findings, report evidence. This is injected reasoning guidance; it does not force the model's internal thought or make every judgment deterministic. |
| 3. Notice a gap              | **Where is the evidence?**      | One finding lacks a source. Show the missing attachment as an editorial question, not a fabricated `GATE_REVIEW: FAIL`. A real failure may replace this only when captured.                                                        |
| 4. Author the boundary       | **Make the check reusable.**    | The client proposes a cite-evidence criterion, then explicitly writes a gate through `resource_manager`. An authored document becomes a checkpoint; it does not appear automatically from observing the gap.                       |
| 5. Continue with context     | **Carry the evidence forward.** | The packet collects a source and continues through the chain. A client-native specialist may contribute evidence, with the same framework/brief passed into its handoff. No automatic correctness guarantee is implied.            |
| 6. Return with a new task    | **Use it next time.**           | A second review request follows the equipped route. The client deliberately attaches the gate or invokes an authored prompt/chain that includes it. A source requirement appears before the findings are returned.                 |
| 7. Resolve to useful work    | **A workflow worth reusing.**   | Show a tangible review artifact: findings, source pointers, next steps. Pull back to the reusable prompt, framework and gate resources. End with Claude Prompts / **The portable workflow layer.**                                 |

Beat 4's `cite-evidence` is a **proposed resource**, not an existing catalog claim. An abbreviated source-derived tool-call specimen may show `resource_manager(resource_type:"gate", action:"create", id:"cite-evidence", …)`. Before recording, the client must author a complete schema-valid request, confirm its successful write, and attach the resulting gate through the documented resource/command contract. The ellipsis specimen is illustration, not a runnable call. Beat 6 must not imply that every future prompt automatically inherits a newly created gate.

A source-citation criterion is model review guidance. If the final story adds an executable check, show the actual command/script, its configured scope and the resulting evidence; shell/script criteria need a chain review. Keep reasoning guidance, self-assessment, structural checks and executable verification visually distinguishable.

### Three spatial metaphors to compare

| Direction                               | Spatial law and material action                                                                                                                                                                                                   | Strength and caveat                                                                                                                                                                                                                                                   |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A · Route landscape**                 | A sparse open terrain gains authored routes, frameworks as surveying scaffolds, and gates as installed checkpoints. A context packet follows the selected chain; an explicit client action places each new resource.              | Makes returning with a new task legible and shows an environment becoming equipped. Avoid portraying reasoning frameworks as physical laws or putting the viewer on a fixed rollercoaster. Scaffolds guide attention; they do not guarantee the traveler's judgments. |
| **B · Workshop city**                   | Distinct work areas house research, review and production. A shared framework provides the architectural grammar; clients carry a brief between benches. New gates are labeled inspection fixtures installed from authored plans. | Makes specialist contributions and tangible outputs concrete. Keep the city from becoming a capability catalog: one task visits only the work areas it needs. Buildings represent reusable resources/practice, not autonomous server processes that execute work.     |
| **C · Literal transit, counterexample** | A ticket/context packet boards a fixed line. Prompts are stations, chain edges are track, gates are turnstiles, framework is signage.                                                                                             | Easy to read, but may imply passive clients, fixed routes and deterministic checks. A rollercoaster exaggerates these liabilities: speed replaces inspection and the passenger cannot author the route. Retain this as a contrast board, not a settled direction.     |

These are materially different spatial laws: an open terrain can be equipped, a workshop organizes acts of making, and transit constrains movement along a preselected line. The comparison should show the same seven narrative beats so the choice is about meaning, not which board has more polish.

## Pacing and editing

The opening uses three short scenes to answer what the project adds in 20 seconds. The interaction slows down for the handoff and review, because those are the differentiators. The longest final hold gives the viewer a concrete asset to inspect. Sound design, if added, supports the visible action; it carries no information needed to understand the story.

Use whole phrase reveals rather than character-by-character typing. Never erase a headline before its read hold ends. A scene has one dominant action and one reading target. Incoming motion occupies the first 1–3 seconds; settled text occupies the rest. Keep all copy inside a 96px safe margin at 1920 × 1080. Prefer headline lengths under 45 characters and body lengths under 120 characters; verify final font size and wrapping in the rendered frames.

Transition rationale:

1. Problem → Identity: cut from clutter to Paper clarity; it introduces the project as the answer to the repeated work.
2. Identity → Compose: carry the same brief into the strip, preserving the viewer's object of attention.
3. Compose → Request: expand one prompt specimen into the authored creative brief, connecting syntax to use.
4. Request → Agents: the brief packet follows Route into specialist lanes; the motion represents context transfer.
5. Agents → Check: collect the specialist work into one packet and stop it at the criteria panel. Amber means attention, not failure.
6. Check → Result: cut to the artifact after the review hold. No color change or symbol implies a verdict that was never recorded.
7. Result → CTA: preserve a thumbnail of the poster while the identity returns; connect the tangible output to reuse.

Boundary transitions must remain within the declared scene durations. Do not overlap scenes by subtracting transition frames from the 2250-frame runtime. No glitch flashes, CRT scanlines, terminal chrome, decorative cursor activity, or simulated loading bars are needed for this draft.

The final phase must produce the artifact, not stop at a recommendation. A client may select Remotion or another JS/TS/Python animation library supported by the production environment. This script makes no promise that the MCP server parses the scene manifest or provides the renderer.

A real production run must supply the owned implementation file scope before an agent writes source. The film does not advertise public availability until MCP installation/discovery has been verified; its continuous draft disclosure remains in force meanwhile.
